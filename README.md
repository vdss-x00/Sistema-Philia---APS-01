## Contexto

Esse projeto tem como objetivo servir de introdução a APIs RESTful para os alunos, abordando conceitos como métodos HTTP, funções assíncronas, controladores, roteamento, variáveis de ambiente, suítes automatizadas de testes, pipelines CI/CD e entre outros.

Para esse projeto em específico, os alunos escolheram criar uma API RESTful que simula uma plataforma de angariação de fundos, semelhante a outras plataformas como GoFundMe ou Vakinha, chamada `Philia`, nome que vem do grego antigo e significa "amizade" ou "afeição".

Com esta API, é possível efetuar operações CRUD com quatro entidades registradas no banco de dados.

>Para as operações de "delete", foi escolhido o uso do soft delete, considerado boa prática na modelagem de banco de dados e combina com a matéria de "Banco de Dados", que os alunos também tiveram esse semestre.

## Entidades e Relacionamentos

Há quatro entidades envolvidas no projeto:

- `Campanha`: Entidade que representa as campanhas de angariação de fundos da plataforma, seja para as mais variadas causas;
- `Organizador`: Entidade que representa o criador das campanahas;
- `Contribuidor`: Entidade que representa a pessoa que contribui, doa, ou apoia uma campanha;
- `Campanha-Contribuidor`: Entidade associativa que representa o relacionamento entre `Campanha` e `Contribuidor`;

Um organizador pode ter várias campanhas, mas uma campanha pertence a apenas um organizador. (1:N)

E uma campanha pode ser apoiada por vários contribuidores, assim como um contribuidor pode apoiar várias campanhas. (N:M)
Assim, sendo necessária a criação de uma entidade associativa entre as duas.

## Regras de Negócio

Principais regras de negócio do projeto, separadas pelos componentes principais e em poucas palavras:

- `Campanhas`: possuem título obrigatório, meta monetária maior ou igual a zero, descrições/imagens com limites e podem ser ativadas ou desativadas.

- `Organizadores`: precisam de nome válido e podem usar descrições e ícones; também podem ser ativados ou desativados.

- `Contribuidores`: possuem nome obrigatório, descrição, ícone e valor total de contribuição, com limites de caracteres e valores monetários válidos.

- `Contribuições`: associam um contribuidor a uma campanha por UUIDs válidos e registram valores não negativos com até duas casas decimais.

- `Validações gerais`: UUIDs, campos obrigatórios, tamanhos máximos e limites de valores são obrigatoriamente respeitados.

- `Exclusão lógica`: contribuintes podem ser marcados como excluídos sem serem removidos definitivamente.

## Configuração e Execução
>Pré-requisito: Ter um projeto ativo no Supabase

A API já está disponível para testes e avaliação por meio do link Vercel, disponível por meio da seção `About` deste repositório.
Mas, se desejar rodar os testes com o seu próprio projeto supabase, siga os passos abaixo.

Antes de rodar `git clone`, vá ao editor SQL do seu projeto e copie e cole o código presente no arquivo `schema.sql`, clique em salvar e depois em `run`, para executar o código e criar as tabelas necessárias.

Após isso, agora sim clone o repositório:
```bash
git clone https://github.com/vdss-x00/Sistema-Philia---APS-01.git
```
Depois rode:
```bash
cd Sistema-Philia---APS-01
```
```bash
code .
```

Agora, estando com o projeto aberto, crie o arquivo .env que será usado para a API. Substitua os valores da chave pública e da chave anônima pelos valores reais do seu projeto.


Por último, rode os seguintes comandos para instalar as dependências necessárias do Node e para iniciar o servidor:
```bash
npm install
```
```bash
npm run dev
```

## Tabelas do Banco de Dados

Há quatro tabelas usadas no projeto:

### organizers
| Coluna | Descrição |
| ------ | --------- |
| id     | Chave primária gerada aleatoriamente <br />e automaticamente pela função randomUUID(). |
| name   | Nome do organizador. |
| description | Descrição do organizador. |
| icon | Atributo VARCHAR que simula imagem de perfil do organizador. |
| active | Atributo booleano que indica se o organizador <br /> está ativo ou não. |
| created_at | Atributo `timestamp` gerado automaticamente pelo Supabase. |
| is_deleted | Atributo booleano que indica se o organizador <br /> foi deletado por meio de soft delete ou não. |

### campaigns
| Coluna | Descrição |
| ------ | --------- |
| id     | Chave primária gerada aleatoriamente <br />e automaticamente pela função randomUUID(). |
| organizer_id | Chave estrangeira da tabela `organizers`, <br /> associando as duas tabelas. |
| title | Nome da Campanha. |
| description | Descrição da Campanha. |
| image | Atributo VARCHAR que simula a imagem de capa <br /> da campanha. |
| goal_amount | Atributo numérico que simula a meta <br/> de doações de uma campanha. |
| active | Atributo booleano que indica se a campanha <br /> está ativa ou não. |
| created_at |  Atributo `timestamp` gerado automaticamente pelo Supabase. |
| updated_at |  Atributo `timestamp` gerado automaticamente pelo Supabase. |
| is_deleted | Atributo booleano que indica se a campanha <br /> foi deletada por meio de soft delete ou não. |

### contributors
| Coluna | Descrição |
| ------ | --------- |
| id     | Chave primária gerada aleatoriamente <br />e automaticamente pela função randomUUID(). |
| name   | Nome do contribuidor. |
| description | Descrição do contribuidor. |
| donation_amount | Atributo numérico que simula o valor de uma doação <br /> de um contribuidor. |
| icon | Atributo VARCHAR que simula imagem de perfil do contribuidor. |
| active | Atributo booleano que indica se o contribuidor <br /> está ativo ou não. |
| created_at | Atributo `timestamp` gerado automaticamente pelo Supabase. |
| is_deleted | Atributo booleano que indica se o contribuidor <br /> foi deletado por meio de soft delete ou não. |

### campaign_contributors
| Coluna | Descrição |
| ------ | --------- |
| campaign_id     | Chave estrangeira que referencia a tabela `campaigns` |
| contributor_id   | Chave estrangeira que referencia a tabela `contributors` |
| donation_amount | Valor numárico que referencia a quantia da doação. |
| created_at | Atributo `timestamp` gerado automaticamente pelo Supabase. |

## Endpoints

### Campanha
| Método |  Rota  | Descrição |
| :------ | :------: | :--------- |
|  `GET` |   `/campaigns`  | Lista todas as campanhas registradas |
|  `GET` | `/campaigns/:id`| Lista uma campanha específica pelo seu id|
| `POST` |`/campaigns`     | Registra uma campanha nova |
| `PUT`  | `/campaigns/:id`| Atualiza uma campanha registrada (selecionada pelo id) |
| `PATCH`| `/campaigns/:id/disable`| Desativa uma campanha (selecionada pelo id) por meio do soft delete  |

### Organizador
| Método |  Rota  | Descrição |
| :------ | :------: | :--------- |
|  `GET` |   `/organizers`  | Lista todas os organizadores registrados |
|  `GET` | `/organizers/:id`| Lista um organizador específico pelo seu id|
| `POST` |`/organizers`     | Registra um organizador novo |
| `PATCH`  | `/organizers/:id`| Atualiza parte do registro de um organizador |
| `PATCH`| `/organizers/:id/disable`| Desativa um organizador (selecionado pelo id) por meio do soft delete |

### Contribuidor
| Método |  Rota  | Descrição |
| :------ | :------: | :--------- |
|  `GET` |   `/contributors`  | Lista todas os contribuidores registrados |
|  `GET` | `/contributors/:id`| Lista um contribuidor específico pelo seu id|
| `POST` |`/contributors`     | Registra um contribuidor novo |
| `PATCH`  | `/contributors/:id`| Atualiza parte do registro de um contribuidor |
| `PATCH`| `/contributors/:id/disable`| Desativa um contribuidor (selecionado pelo id) por meio do soft delete |

### Campanha-Contribuidor
| Método |  Rota  | Descrição |
| :------ | :------: | :--------- |
|  `GET` |   `/campaign-contributors`  | Lista todas as contribuições registradas |
|  `GET` | `/campaign-contributors/:campaign_id/:contributor_id`| Lista uma contribuição específica por <br /> sua ids de campanha e contribuidor|
| `POST` |`/campaign-contributors`     | Registra uma contribuição novo |
| `PATCH`  | `/campaign-contributors/:campaign_id/:contributor_id` | Atualiza parte do registro de uma contribuição |

## Exemplos de Requisições

Antes de começar, é necessário lembrar que as duas tabelas estão vazias. Por isso, abra o Postman e efetue uma operação POST no endpoint `/organizers`.

>Importante lembrar que a API só aceita um objeto JSON por vez, e não um array.
Exemplo:
```text
{
    "name": "Jéssica",
    "description": "Organizadora de eventos de caridade para crianças com câncer.",
    "icon": "❤️"
}
``` 

Deve resultar em algo assim:
```text
{
    "id": "00315c15-b3c0-4317-a2b8-54d67226156b",
    "name": "Jéssica",
    "description": "Organizadora de eventos de caridade para crianças com câncer.",
    "icon": null,
    "active": true,
    "created_at": "2026-09-29T02:42:40.344568+00:00",
    "is_deleted": false
  },
```
>Os campos que não foram incluídos no input são gerados automaticamente pelo Supabase.

Após criar seu primeiro organizador, crie uma campanha com POST no endpoint `/campaigns`, lembrando-se de copiar a id gerada no último exemplo:
```text
{
    "organizer_id": "00315c15-b3c0-4317-a2b8-54d67226156b",
    "title": "Ajude as crianças do nosso hospital!",
    "description": "Nos ajude a conseguir medicamentos!",
    "goal_amount": 6500.00,
    "active": false
}
```

Resultado:
```text
{
    "id": "a874b695-eb26-40fd-b4ea-4b0790c52dd2",
    "organizer_id": "00315c15-b3c0-4317-a2b8-54d67226156b",
    "title": "Ajude as crianças do nosso hospital!",
    "description": "Nos ajude a conseguir medicamentos!",
    "image": null,
    "goal_amount": 6500,
    "active": false,
    "created_at": "2026-09-29T02:59:16.820711+00:00",
    "updated_at": "2026-09-29T02:59:16.820711+00:00",
    "is_deleted": false
}
```
Agora, para mudar um ou mais atributos, efetue uma operação PUT no endpoint `/campaigns/:id`, trocando o ":id" pelo id gerado pelo Supabase:
>Essa API permite efetuar operações PUT da mesma maneira que uma operação PATCH, especificando apenas o atributo que deseja modificar.
```text
{
    "active": true
}
```

Resultado:
```text
{
    "id": "a874b695-eb26-40fd-b4ea-4b0790c52dd2",
    "organizer_id": "00315c15-b3c0-4317-a2b8-54d67226156b",
    "title": "Ajude as crianças do nosso hospital!",
    "description": "Nos ajude a conseguir medicamentos!",
    "image": null,
    "goal_amount": 6500,
    "active": true,
    "created_at": "2026-09-29T02:59:16.820711+00:00",
    "updated_at": "2026-09-29T02:59:16.820711+00:00",
    "is_deleted": false
}
```

Para completar o ciclo de CRUD, efetue uma operação PATCH no endpoint `/campaigns/:id/disable` para desativar a campanha que você registrou.

Exemplo:
```text
{
    "id": "a874b695-eb26-40fd-b4ea-4b0790c52dd2",
```

## Testes Automatizados

Neste projeto, é possível rodar uma suíte de testes unitários e de integração através das ferramentas `Vitest` e `Supertest`, respectivamente.

Os arquivos de teste são organizados da seguinte maneira:
```text
tests/
├── campaign/
|   └── Campaign.integration.test.ts
|   └── Campaign.test.ts
├── campaign_contributor/
|   └── CampaignContributor.integration.test.ts
|   └── CampaignContributor.test.ts
├── contributor/
|   └── Contributor.integration.test.ts
|   └── Contributor.test.ts
├── organizer/
|   └── Organizer.integration.test.ts
|   └── Organizer.test.ts
```

Para rodar a suíte, rode um destes três comandos no terminal:


Para rodar os testes uma única vez:
```bash
npm test
```

Para rodar os testes em modo de monitoramento (watch mode), em que roda os testes automaticamente após mudanças no código:
```bash
npm run test:watch
```

Para rodar os testes e gerar um relatório de cobertura de código:
```bash
npm run test:coverage
```

Ao rodar `npm run test:coverage`, se todos os testes forem bem-sucedidos, será gerado um relatório de cobertura de código dos arquivos de teste

Exemplo de relatório de cobertura de código:
